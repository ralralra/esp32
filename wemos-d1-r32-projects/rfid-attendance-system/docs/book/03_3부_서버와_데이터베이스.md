# 3부 — 서버와 데이터베이스 만들기

이 부에서 만드는 것은 눈에 보이는 결과가 적습니다. LED가 깜빡이지도, 소리가 나지도 않습니다. 하지만 브라우저 주소창에 주소를 입력하면 구글 시트에 표가 생기고 데이터가 쌓이는 것을 직접 볼 수 있습니다. **"내가 서버에 말을 걸고 있다"**는 감각을 만드는 것이 이 부의 목표입니다.

# 7장 세션과 폴링 — 서버 설계의 핵심 개념

코드를 보기 전에 두 개념을 확실히 해 둡시다. 이 둘만 이해하면 3부의 코드 대부분이 자명해집니다.

## 7.1 세션: "지금 카드를 기다리는 중"이라는 메모

앱이 [출석체크 시작]을 누른 순간부터, 학생이 태그하거나 30초가 지날 때까지의 기간을 **세션(session)** 이라고 부릅니다.

세션의 실체는 무엇일까요? 거창한 것이 아닙니다. **서버가 적어 둔 메모 한 장**입니다.

```
누가:   DEV001 리더기가
무엇을: 출석 모드로 (attend)
언제까지: 30초 동안
누구를: 김세이프를 대상으로
교시:   1교시
지각기준: 09:10 이후면 지각
상태:   기다리는 중 (waiting)
결과:   아직 없음
```

이 메모가 있으면 ESP32는 "지금 카드를 받아야 하는구나"를 알고, 없으면 "할 일 없구나" 하고 대기합니다. 태그가 처리되면 서버가 이 메모에 결과를 적고 상태를 '완료(done)'로 바꿉니다. 그러면 앱이 그 결과를 가져갑니다.

**세션은 리더기 한 대당 하나입니다.** 메모를 리더기 이름(`DEV001`)으로 서랍에 넣어 두기 때문입니다. 같은 이름으로 새 메모를 넣으면 이전 것을 덮어씁니다. 교실이 여러 개면 리더기 이름을 다르게 주면 되고, 그러면 세션도 자연히 분리됩니다.

## 7.2 캐시와 자동 만료 — 타이머 없이 30초를 세는 법

메모를 어디에 적어 둘까요? 구글 시트에 적을 수도 있습니다. 하지만 우리는 **캐시(Cache)** 라는 임시 저장소를 씁니다. Apps Script가 제공하는 `CacheService`입니다.

캐시를 쓰는 이유가 아주 좋습니다. 캐시에 넣을 때 **"몇 초 동안 보관할지"를 함께 지정할 수 있고, 그 시간이 지나면 알아서 사라지기 때문**입니다.

```javascript
CacheService.getScriptCache().put(키, 값, 30);   // 30초 뒤 자동 삭제
```

이 한 줄 덕분에 **"30초를 세다가 세션을 지운다"는 코드를 우리가 짤 필요가 없습니다.** 30초가 지나면 메모는 저절로 없어지고, 그때부터 서버는 "그런 세션 없는데요"라고 답하게 됩니다. 앱은 그 답을 보고 "시간 초과" 화면을 띄우면 됩니다.

**질문: 서버가 직접 30초를 세다가 지우는 방식과 비교하면 어떤가요?**

직접 세려면 타이머를 걸어야 하고, 서버가 잠들거나 재시작하면 타이머가 사라집니다. 어느 세션이 언제 만료되는지 목록도 관리해야 합니다. 캐시의 자동 만료를 쓰면 그 모든 것이 필요 없습니다. **"기능을 직접 만들지 않고, 이미 있는 성질을 이용해 문제를 없애는 것"** — 좋은 설계의 전형적인 모습입니다.

> **💡 수업 활용 팁**
> 실습으로 바로 확인시킬 수 있습니다. 브라우저에서 세션을 시작한 뒤 **30초 안에** 폴링 주소를 열면 `ATTEND`가 나오고, **30초가 지난 뒤에** 열면 `IDLE`이 나옵니다. 아무 코드도 실행되지 않았는데 답이 바뀌는 것을 보면 '자동 만료'가 실감 납니다.

## 7.3 두 개의 폴링, 하나의 세션

세션이라는 메모 한 장을 두고 **두 방향의 폴링**이 오갑니다.

| 누가 | 얼마나 자주 | 무엇을 묻나 | 어떤 답을 받나 |
|---|---|---|---|
| **ESP32** | 2초마다 | "할 일 있나요?" | `IDLE` / `ATTEND` / `REGISTER` — **한 단어** |
| **앱** | 1초마다 | "결과 나왔나요?" | `{state, mode, result}` — **JSON** |

같은 메모를 보는데 답의 모양이 다릅니다. 왜 그럴까요?

**ESP32에게 한 단어로 답하는 이유:** ESP32는 작은 마이크로컨트롤러입니다. JSON을 해석하려면 라이브러리를 추가로 넣어야 하고, 메모리도 더 씁니다. 그런데 ESP32가 알아야 할 것은 "지금 무슨 모드냐" 하나뿐입니다. 그렇다면 `ATTEND`라는 한 단어면 충분합니다. 코드도 `if (res == "ATTEND")` 한 줄이면 끝납니다.

**앱에게 JSON으로 답하는 이유:** 앱은 브라우저에서 도는 자바스크립트입니다. JSON은 자바스크립트의 모국어나 다름없어서 해석이 공짜입니다. 그리고 앱은 이름·상태·시각·실패 사유 등 여러 값을 한꺼번에 받아야 합니다.

**받는 쪽의 형편에 맞춰 같은 정보를 다르게 포장하는 것** — 이것도 설계입니다. 학생들에게 "왜 굳이 두 가지로 만들었을까?"를 물어보면 좋은 토론이 됩니다.

# 8장 구글 시트를 데이터베이스로 쓰기

## 8.1 세 개의 시트, 세 가지 역할

'데이터베이스'라는 말이 어렵게 들린다면, **자동으로 채워지는 엑셀**이라고 생각하면 됩니다. 우리는 구글 시트 하나에 표 세 개를 두고 씁니다.

| 시트 | 역할 | 누가 채우나 |
|---|---|---|
| **학생명단** | 어느 카드가 누구의 것인지 | 등록할 때 서버가 자동으로 |
| **출석기록** | 언제 누가 출석/지각했는지 | 태그할 때마다 서버가 자동으로 |
| **교시설정** | 몇 시부터 지각인지 | **사람이 직접** (학교 시간표에 맞게) |

세 시트 모두 **미리 만들 필요가 없습니다.** 빈 시트에서 시작해도, 서버가 첫 요청을 받는 순간 세 개를 한꺼번에 머리글과 함께 만듭니다. 그 원리는 12.5절에서 봅니다.

## 8.2 학생명단 — UID와 사람을 잇는 표

| A: UID | B: 이름 | C: 학년 | D: 반 | E: 번호 | F: 등록일시 |
|---|---|---|---|---|---|
| 6F3178D9 | 김세이프 | 1 | 3 | 7 | 2026-08-11 12:49:03 |
| A1B2C3D4 | 이하늘 | 1 | 3 | 8 | 2026-08-11 12:51:20 |

이 표의 존재 이유는 단 하나 — **번호를 사람으로 바꾸는 것**입니다. 리더기는 `6F3178D9`밖에 모릅니다. 이 표가 있어야 "김세이프"라는 이름이 나옵니다.

데이터베이스 용어로는 이런 연결을 **관계(relation)** 라고 하고, 표와 표를 이어 붙이는 것을 조인(join)이라고 합니다. 출석기록의 UID로 학생명단의 이름을 찾는 우리 코드가 바로 그 일을 손으로 하는 것입니다.

> **💡 수업 활용 팁**
> 칠판에 두 표를 나란히 그리고, 출석기록의 UID에서 학생명단의 같은 UID로 화살표를 그어 보여 주세요. 이 그림 하나가 12.5절의 `findStudent()` 함수를 이해하는 밑돌이 됩니다.

## 8.3 출석기록 — 자동으로 쌓이는 출석부

| A: 날짜 | B: 시각 | C: 교시 | D: UID | E: 이름 | F: 상태 | G: 리더기 |
|---|---|---|---|---|---|---|
| 2026-08-11 | 09:03:12 | 1 | 6F3178D9 | 김세이프 | 출석 | DEV001 |
| 2026-08-11 | 09:14:51 | 1 | A1B2C3D4 | 이하늘 | 지각 | DEV001 |

태그 한 번에 한 줄씩 쌓입니다. 여기서 설계상 선택이 하나 있습니다. **UID와 이름을 둘 다 저장한다**는 점입니다.

이름은 학생명단에 있으니 UID만 저장해도 나중에 찾을 수 있습니다. 그런데 왜 이름까지 넣었을까요? **기록 당시의 사실을 그대로 남기기 위해서**입니다. 나중에 학생명단에서 그 학생이 삭제되거나 이름이 바뀌어도, 출석기록은 "그날 그 시각에 김세이프가 출석했다"는 사실을 그대로 보존합니다. 그리고 사람이 시트를 열었을 때 바로 읽을 수 있다는 실용적 이점도 큽니다.

이런 방식을 **비정규화**라고 하며, 중복을 감수하고 조회 편의와 기록 보존을 얻는 흔한 선택입니다.

## 8.4 교시설정 — 지각의 기준을 정하는 표

| A: 교시 | B: 시작시각 | C: 지각기준 |
|---|---|---|
| 1 | 09:00 | 09:10 |
| 2 | 10:00 | 10:10 |
| ... | ... | ... |

이 표만 사람이 직접 관리합니다. 처음 만들어질 때 1~7교시의 기본값이 채워지므로, 학교 시간표에 맞게 시각을 고치면 됩니다.

이 작은 표에 중요한 설계 사상이 담겨 있습니다. **바뀔 수 있는 값을 코드가 아니라 데이터로 두는 것**입니다.

지각 기준을 코드 안에 `if (시각 > "09:10")`처럼 박아 두면, 시간표가 바뀔 때마다 개발자가 코드를 고치고 다시 배포해야 합니다. 표에 두면 선생님이 시트에서 숫자만 고치면 되고, 그 즉시 반영됩니다.

**"자주 바뀌는 것은 데이터로, 잘 바뀌지 않는 것은 코드로"** — 이 원칙은 어떤 프로그램을 만들든 유용합니다.

# 9장 중계 서버 배포하기

## 9.1 10분 만에 서버 갖기

**① 빈 시트 만들기**
[sheets.new](https://sheets.new)로 새 구글 시트를 만듭니다. 이름은 자유롭게(예: 스마트출석체크). 시트 탭은 만들지 않아도 됩니다.

**② Apps Script 열기**
시트 메뉴에서 **확장 프로그램 → Apps Script**를 클릭합니다. 새 창이 열리고 `Code.gs`라는 빈 파일에 `function myFunction() {}` 정도가 들어 있습니다. **전부 지웁니다.**

**③ relay.gs 붙여넣기**
저장소의 `relay.gs` 전체를 복사해 붙여넣고 저장합니다(Ctrl+S).

> `github.com/ralralra/esp32/blob/main/wemos-d1-r32-projects/rfid-attendance-system/apps_script/relay.gs`

**④ 웹 앱으로 배포**
오른쪽 위 **배포 → 새 배포**를 누르고, 유형에서 **웹 앱**을 고릅니다. 설정은 이렇게 합니다.

- 실행 계정: **나**
- 액세스 권한: **모든 사용자** ← 이게 핵심입니다

**배포**를 누르면 권한 승인 창이 뜹니다. 승인하면 아래와 같은 주소가 나옵니다. **이 주소를 복사해 두세요.**

```
https://script.google.com/macros/s/AKfy...긴문자열.../exec
```

이 주소가 우리 서버의 주소입니다. 앞으로 **앱과 ESP32 펌웨어 양쪽에** 이 주소를 넣습니다.

> **📌 권한 승인 창에서 당황하지 않기**
> "Google에서 확인하지 않은 앱입니다"라는 경고가 뜹니다. 직접 만든 스크립트라 당연한 것이니, **고급 → (프로젝트 이름)(으)로 이동**을 눌러 진행하면 됩니다. 학생들이 여기서 가장 많이 멈추므로 미리 안내해 두세요.

## 9.2 액세스 권한을 "모든 사용자"로 해야 하는 이유

액세스 권한을 "나만" 또는 "구글 계정이 있는 사용자"로 두면 시스템이 동작하지 않습니다. **ESP32는 구글에 로그인할 수 없기 때문**입니다.

브라우저라면 이미 로그인되어 있어서 문제가 없지만, ESP32는 그저 주소를 열고 답을 받아 오는 단순한 장치입니다. 로그인 화면이 나오면 아무것도 할 수 없습니다.

그래서 "모든 사용자"로 열어 둡니다. 다만 이는 **주소를 아는 사람은 누구나 요청할 수 있다**는 뜻이기도 합니다. 교육용 시스템에서는 주소가 충분히 길고 복잡해서(추측이 사실상 불가능) 이 정도로 충분하지만, 실제 서비스라면 요청에 비밀 키를 함께 보내 확인하는 절차를 넣어야 합니다. 좋은 심화 과제입니다.

## 9.3 브라우저로 첫 요청 보내 보기

ESP32 없이, 브라우저 주소창만으로 서버 전체를 시험할 수 있습니다. 배포 주소를 `URL`이라고 할 때 아래를 차례로 열어 보세요.

| 순서 | 주소 | 기대하는 응답 |
|---|---|---|
| ① | `URL?action=periods` | 교시 목록 JSON (**이때 시트 3개가 한 번에 생깁니다**) |
| ② | `URL?action=start&mode=register&device=DEV001&name=김세이프&grade=1&klass=3&number=7` | `{"ok":true,"timeout":30}` |
| ③ | `URL?action=poll&device=DEV001` | `REGISTER` |
| ④ | `URL?action=tag&device=DEV001&uid=A1B2C3D4` | `OK_REG,김세이프` |
| ⑤ | `URL?action=status&device=DEV001` | `{"state":"done",...}` |
| ⑥ | `URL?action=start&mode=attend&device=DEV001&name=김세이프&period=1` | `{"ok":true,...}` |
| ⑦ | `URL?action=tag&device=DEV001&uid=A1B2C3D4` | `OK,김세이프,출석,09:03:12` |

①을 연 직후 시트로 돌아가 보세요. **학생명단·출석기록·교시설정 세 탭이 스르륵 생겨 있습니다.** 이 순간이 3차시의 하이라이트입니다. 화면을 미러링해 다 함께 보면 좋습니다.

④가 끝나면 학생명단에 한 줄, ⑦이 끝나면 출석기록에 한 줄이 생겨 있어야 합니다.

여기서 ③과 ④가 바로 **ESP32인 척하는 것**입니다. ESP32가 하는 일이 결국 이 주소를 여는 것이 전부이므로, 브라우저로 똑같이 할 수 있습니다. 이 사실을 알아 두면 나중에 문제가 생겼을 때 "장치 문제인지 서버 문제인지"를 바로 가려낼 수 있습니다.

## 9.4 수정했는데 반영되지 않을 때

Apps Script에서 가장 많이 겪는 혼란입니다. **코드를 고치고 저장(Ctrl+S)해도 배포된 웹 앱에는 반영되지 않습니다.**

반영하려면 **배포 → 배포 관리 → 연필(수정) 아이콘 → 버전: 새 버전 → 배포**를 해야 합니다.

이때 "새 배포"를 또 만들면 **URL이 바뀌어 버립니다.** 그러면 앱과 펌웨어에 넣어 둔 주소를 전부 고쳐야 하니, 반드시 기존 배포를 **수정**하세요.

# 10장 서버 코드 읽기 ① — 요청을 나누는 창구

> 이 장부터의 전체 코드: `github.com/ralralra/esp32/blob/main/wemos-d1-r32-projects/rfid-attendance-system/apps_script/relay.gs`

## 10.1 route() — 하나의 주소, 여덟 가지 일

우리 서버의 주소는 하나뿐입니다. 그런데 해야 할 일은 여덟 가지입니다. 어떻게 구분할까요?

**요청에 붙어 오는 `action` 값으로 구분합니다.**

```javascript
function route(e) {
  var p = (e && e.parameter) || {};
  switch (p.action) {
    // ── 앱이 부르는 것 ──
    case 'start':    return startSession(p);
    case 'status':   return sessionStatus(p);
    case 'cancel':   return cancelSession(p);
    case 'students': return listStudents(p);
    case 'records':  return listRecords(p);
    case 'periods':  return listPeriods(p);
    // ── ESP32가 부르는 것 ──
    case 'poll':     return devicePoll(p);
    case 'tag':      return deviceTag(p);
    default: return text('ERR,unknown_action');
  }
}
```

`e.parameter`에는 주소 뒤에 붙여 보낸 값들이 담겨 있습니다. `URL?action=poll&device=DEV001`로 요청하면 `p.action`은 `'poll'`, `p.device`는 `'DEV001'`이 됩니다.

`switch`문은 값에 따라 갈 길을 나누는 문법입니다. `p.action`이 `'poll'`이면 `devicePoll(p)`를, `'tag'`면 `deviceTag(p)`를 부릅니다. 어느 것도 아니면 마지막 `default`로 가서 오류 메시지를 돌려줍니다.

> **📌 민원 창구 비유**
> `route()`는 시청의 종합 민원 창구입니다. 시민(요청)이 오면 용건(action)을 듣고 담당 부서(함수)로 안내합니다. 창구 직원은 실제 업무를 처리하지 않고 **안내만** 합니다. 코드도 마찬가지로, `route()`는 어떤 함수를 부를지만 정하고 실제 일은 각 함수가 합니다. 이렇게 **"나누는 일"과 "하는 일"을 분리**하면 새 기능을 추가할 때 `case` 한 줄과 함수 하나만 더하면 됩니다.

## 10.2 doGet과 doPost

```javascript
function doGet(e)  { return route(e); }
function doPost(e) { return route(e); }
```

Apps Script는 정해진 이름의 함수를 자동으로 부릅니다. 웹 앱에 GET 방식 요청이 오면 `doGet`, POST 방식이면 `doPost`를 찾습니다. 우리는 둘 다 같은 `route()`로 보냈습니다.

**우리는 GET만 씁니다.** 이유는 두 가지입니다.

**첫째, ESP32에서 단순합니다.** 주소를 만들어 열기만 하면 됩니다.

**둘째, 브라우저에서 CORS 문제가 없습니다.** 브라우저는 다른 서버로 요청을 보낼 때 보안 검문을 합니다(자세한 것은 16.3절). 그런데 단순한 GET 요청은 검문 없이 통과합니다. 이 성질 덕분에 앱 쪽 코드도 간단해집니다.

## 10.3 왜 앱에는 JSON, 장치에는 텍스트인가

7.3절에서 이미 이유를 봤습니다. 코드로는 이렇게 나뉩니다.

```javascript
function text(s) {
  return ContentService.createTextOutput(s)
    .setMimeType(ContentService.MimeType.TEXT);
}

function json(obj) {
  return ContentService.createTextOutput(JSON.stringify(obj))
    .setMimeType(ContentService.MimeType.JSON);
}
```

두 함수 모두 결국 글자를 돌려주지만, `json()`은 객체를 JSON 형식 문자열로 바꾸고(`JSON.stringify`) 형식을 JSON이라고 표시합니다.

응답을 만드는 코드가 이 두 함수로 모여 있다는 점도 눈여겨보세요. 나중에 응답 형식을 바꿔야 할 때 이 두 곳만 고치면 됩니다. **같은 일을 하는 코드를 한곳에 모으는 것**은 프로그래밍의 기본 습관입니다.

# 11장 서버 코드 읽기 ② — 세션을 만들고 확인하기

## 11.1 startSession() — 메모를 남기다

앱의 [출석체크 시작]과 [등록 시작] 버튼이 부르는 함수입니다.

```javascript
function startSession(p) {
  var timeout = Math.min(Math.max(parseInt(p.timeout || '30', 10), 10), 300);

  // 지각 기준: 없으면 교시설정 시트에서 찾는다
  var lateAfter = p.lateAfter || '';
  if (p.mode === 'attend' && !lateAfter && p.period)
    lateAfter = findLateAfter(p.period);

  var sess = { mode: p.mode, state: 'waiting',
    device: p.device, name: p.name || '',
    period: p.period || '',
    lateAfter: lateAfter, result: null };

  // timeout초 뒤 자동 만료되는 캐시에 저장
  CacheService.getScriptCache().put(
    cacheKey(p.device), JSON.stringify(sess), timeout);

  return json({ ok: true, timeout: timeout });
}
```

**첫 줄의 이상한 계산부터 봅시다.**

```javascript
var timeout = Math.min(Math.max(parseInt(p.timeout || '30', 10), 10), 300);
```

안쪽부터 읽습니다.
- `p.timeout || '30'` — 값이 안 왔으면 `'30'`을 쓴다
- `parseInt(..., 10)` — 문자열 `'30'`을 숫자 30으로 바꾼다 (10은 10진수라는 뜻)
- `Math.max(..., 10)` — 10보다 작으면 10으로 올린다
- `Math.min(..., 300)` — 300보다 크면 300으로 내린다

결국 **어떤 값이 들어와도 10~300 사이로 만드는** 안전장치입니다. 누군가 `timeout=99999`를 보내도 300이 됩니다.

이런 처리를 **입력 검증**이라고 합니다. 서버는 바깥에서 오는 값을 절대 그대로 믿지 않습니다. 실수든 장난이든 이상한 값이 들어와도 서버가 망가지지 않게 만드는 것 — 서버 프로그래밍의 기본자세입니다.

**둘째, 지각 기준을 채워 넣습니다.**

앱이 `lateAfter`를 직접 보내면 그것을 쓰고, 안 보냈으면 `findLateAfter(p.period)`로 교시설정 시트에서 찾아옵니다. 이렇게 해 두면 앱은 교시 번호만 알면 되고, 지각 기준은 시트에서 관리됩니다(8.4절의 사상 그대로입니다).

**셋째, 메모를 만들어 캐시에 넣습니다.**

`sess` 객체가 7.1절에서 본 그 메모입니다. `state: 'waiting'`으로 시작하는 것에 주목하세요. 이 값이 나중에 `'done'`으로 바뀌는 것이 12장의 이야기입니다.

`JSON.stringify(sess)`로 객체를 문자열로 바꿔 저장합니다. 캐시에는 문자열만 넣을 수 있기 때문입니다. 꺼낼 때는 반대로 `JSON.parse`로 되돌립니다.

## 11.2 devicePoll() — 장치에게는 한 단어로

```javascript
function devicePoll(p) {
  var sess = loadSession(p.device);
  if (!sess || sess.state !== 'waiting') return text('IDLE');
  return text(sess.mode === 'register' ? 'REGISTER' : 'ATTEND');
}
```

세 줄입니다. 하는 일도 단순합니다.

1. 세션 메모를 꺼내 본다
2. 메모가 없거나(`!sess`) 이미 처리가 끝났으면(`state !== 'waiting'`) → `IDLE`
3. 기다리는 중이면 모드에 따라 → `REGISTER` 또는 `ATTEND`

`조건 ? A : B`는 삼항 연산자로, "조건이 참이면 A, 아니면 B"라는 뜻입니다. `if`문을 짧게 쓴 것입니다.

여기서 중요한 것은 **세션이 만료되면 `loadSession`이 `null`을 돌려주고, 자동으로 `IDLE`이 된다**는 점입니다. 만료를 처리하는 코드가 따로 없습니다. 캐시가 대신해 주기 때문입니다(7.2절).

## 11.3 sessionStatus() — 앱에게는 JSON으로

```javascript
function sessionStatus(p) {
  var sess = loadSession(p.device);
  if (!sess) return json({ state: 'none' });
  return json({ state: sess.state, mode: sess.mode, result: sess.result });
}
```

앱이 1초마다 부르는 함수입니다. 앱은 돌아온 `state` 값 하나로 화면을 결정합니다.

| state | 뜻 | 앱이 할 일 |
|---|---|---|
| `none` | 세션이 없다 (만료됐거나 취소됨) | "시간 초과" 화면 |
| `waiting` | 아직 태그를 기다리는 중 | 카운트다운 계속 |
| `done` | 처리 완료, `result`에 결과 있음 | 결과 화면 표시 |

`devicePoll`과 `sessionStatus`를 나란히 놓고 보면, **같은 세션 메모를 서로 다른 방식으로 보여 주고 있을 뿐**임이 분명히 드러납니다.

## 11.4 loadSession()과 캐시의 생명주기

```javascript
function cacheKey(device) { return 'sess_' + device; }

function loadSession(device) {
  if (!device) return null;
  var raw = CacheService.getScriptCache().get(cacheKey(device));
  return raw ? JSON.parse(raw) : null;
}
```

`cacheKey()`는 리더기 이름 앞에 `sess_`를 붙여 캐시의 열쇠를 만듭니다. `DEV001`이면 `sess_DEV001`이 됩니다. 이런 접두사를 붙이면 나중에 다른 용도로 캐시를 쓸 때 이름이 부딪히지 않습니다.

`loadSession()`은 캐시에서 문자열을 꺼내 객체로 되돌립니다. 없으면 `null`을 돌려줍니다.

세션 메모의 일생을 정리하면 이렇습니다.

```
[startSession] 만들어짐 (state: waiting, 30초 시한)
      │
      ├─ 태그됨 → [deviceTag] state: done으로 갱신, 시한 60초로 연장
      │              └─ 앱이 결과를 가져간 뒤 60초 지나면 사라짐
      │
      └─ 아무도 태그 안 함 → 30초 뒤 캐시에서 자동 소멸
                              └─ 이후 poll은 IDLE, status는 none
```

# 12장 서버 코드 읽기 ③ — 태그를 처리하기

이 장이 서버의 심장입니다. 실제로 판단하고 기록하는 일이 모두 여기서 일어납니다.

## 12.1 deviceTag() — 모든 태그가 지나가는 관문

ESP32가 카드를 읽으면 이 주소를 엽니다.

```
URL?action=tag&device=DEV001&uid=6F3178D9
```

```javascript
function deviceTag(p) {
  if (!p.device || !p.uid) return text('ERR,param');

  var lock = LockService.getScriptLock();   // 동시 태그 보호
  lock.waitLock(5000);
  try {
    var sess = loadSession(p.device);
    if (!sess || sess.state !== 'waiting') return text('IDLE');

    var uid = String(p.uid).toUpperCase();
    var out = (sess.mode === 'register')
      ? doRegister(sess, uid)
      : doAttend(sess, uid);

    // 결과를 남기고 세션 완료 처리 (60초 유지)
    sess.state = 'done';
    CacheService.getScriptCache().put(
      cacheKey(p.device), JSON.stringify(sess), 60);

    return text(out);
  } finally {
    lock.releaseLock();
  }
}
```

흐름은 이렇습니다.

1. 필수 값(device, uid)이 왔는지 확인
2. 잠금을 건다
3. 세션이 있고 기다리는 중인지 확인 — 아니면 `IDLE`
4. UID를 대문자로 통일 (펌웨어에서도 대문자로 보내지만 한 번 더)
5. **모드에 따라 등록 또는 출석 처리**
6. 결과를 세션에 적고 `done`으로 바꿔 60초 더 보관
7. 잠금을 푼다

5번이 실제 일이고, 나머지는 그 일이 안전하게 이루어지도록 감싸는 껍데기입니다.

**60초 연장에 주의하세요.** 태그 처리가 끝나면 세션의 남은 시간이 몇 초든 상관없이 60초로 다시 설정됩니다. 앱이 결과를 가져갈 시간을 넉넉히 주기 위해서입니다. 이 처리가 없으면, 29초에 태그된 경우 1초 만에 메모가 사라져 앱이 결과를 못 볼 수도 있습니다.

## 12.2 잠금(Lock) — 두 사람이 동시에 태그하면

`LockService`는 **한 번에 한 요청만 이 구간을 지나가게** 만듭니다.

왜 필요할까요? 시트에 줄을 추가하는 일은 "마지막 줄을 찾아서 그 아래에 쓴다"는 두 단계로 이루어집니다. 두 요청이 동시에 "마지막 줄"을 찾으면 같은 줄을 가리키게 되고, 한 줄이 다른 줄을 덮어써서 기록이 사라질 수 있습니다.

`waitLock(5000)`은 "이미 누가 들어가 있으면 최대 5초까지 기다린다"는 뜻입니다.

```javascript
  try {
    ... 실제 작업 ...
  } finally {
    lock.releaseLock();
  }
```

`try...finally`는 **"무슨 일이 있어도 `finally` 안의 코드는 실행한다"** 는 문법입니다. 중간에 오류가 나서 함수가 중단되더라도 잠금은 반드시 풀립니다. 잠금을 풀지 않으면 다음 요청들이 영원히 기다리게 되므로 이 처리는 필수입니다.

> **📌 화장실 문 비유**
> 잠금은 화장실 문 잠금장치입니다. 한 명이 들어가면 잠그고, 나올 때 엽니다. `try...finally`는 "안에서 무슨 일이 있어도 나올 때는 반드시 문을 연다"는 약속입니다. 문을 잠근 채 사라지면 아무도 못 쓰게 되니까요.

## 12.3 doRegister() — 등록이란 표에 한 줄 쓰는 일

```javascript
function doRegister(sess, uid) {
  var sheet = getSheet('학생명단',
    ['UID','이름','학년','반','번호','등록일시']);

  // 이미 등록된 카드인지 확인
  var found = findStudent(uid);
  if (found) {
    sess.result = { ok: false, reason: 'dup', name: found.name };
    return 'DUP,' + found.name;
  }

  // 학생명단에 한 줄 추가 = 등록 완료
  sheet.appendRow([uid, sess.name, sess.grade, sess.klass,
    sess.number, now('yyyy-MM-dd HH:mm:ss')]);

  sess.result = { ok: true, name: sess.name, uid: uid };
  return 'OK_REG,' + sess.name;
}
```

'등록'이라는 거창한 말의 실체가 `appendRow()` 한 줄이라는 것 — 이 사실이 학생들에게 주는 인상이 큽니다. 시트를 열어 방금 생긴 줄을 직접 확인시켜 주세요.

**중복 검사**를 먼저 하는 것에 주목하세요. `findStudent(uid)`로 그 카드가 이미 등록되어 있는지 보고, 있으면 거절합니다. 카드 한 장이 두 사람의 것이 될 수는 없기 때문입니다.

**결과를 두 곳에 남기는 패턴**도 눈여겨보세요.
- `sess.result = {...}` — 앱이 가져갈 상세한 결과
- `return 'OK_REG,' + ...` — ESP32가 받을 한 줄

한 번의 처리로 두 상대에게 각각 알맞은 형태로 답하는 것입니다.

## 12.4 doAttend() — 세 개의 문지기와 지각 판정

출석 처리는 검사가 셋입니다. 모두 통과해야 기록됩니다.

```javascript
function doAttend(sess, uid) {
  // ① 등록된 카드인가?
  var student = findStudent(uid);
  if (!student) {
    sess.result = { ok: false, reason: 'unknown', uid: uid };
    return 'UNKNOWN';
  }

  // ② 대상 학생이 맞는가?
  if (sess.name && sess.name !== student.name) {
    sess.result = { ok: false, reason: 'mismatch', name: student.name };
    return 'MISMATCH,' + student.name;
  }

  // ③ 이미 이번 교시에 출석했는가?
  //    (출석기록에서 날짜·교시·UID가 모두 같은 줄을 찾는다)
  ...
  if (이미기록있음) return 'ALREADY,' + student.name;

  // 지각 판정
  var time = now('HH:mm:ss');
  var status = '출석';
  if (sess.lateAfter && time > sess.lateAfter + ':00') status = '지각';

  // 기록
  sheet.appendRow([today, time, sess.period, uid,
    student.name, status, sess.device]);

  sess.result = { ok: true, name: student.name, status: status, time: time };
  return 'OK,' + student.name + ',' + status + ',' + time;
}
```

**문지기 ① 미등록 카드 (UNKNOWN)**
학생명단에 없는 카드입니다. 아직 등록하지 않았거나 외부인의 카드입니다.

**문지기 ② 대상 불일치 (MISMATCH)**
앱에서 "김세이프"를 대상으로 지정했는데 다른 학생의 카드가 태그된 경우입니다. `sess.name`이 비어 있으면(전체 대상 세션) 이 검사는 건너뜁니다 — 등록된 학생 누구나 태그할 수 있습니다.

**문지기 ③ 중복 출석 (ALREADY)**
같은 날, 같은 교시, 같은 카드가 이미 기록되어 있으면 다시 기록하지 않습니다. 실수로 두 번 태그해도 출석부가 지저분해지지 않습니다.

**그리고 지각 판정**

```javascript
  if (sess.lateAfter && time > sess.lateAfter + ':00') status = '지각';
```

`time`은 `"09:14:51"`, `sess.lateAfter`는 `"09:10"`입니다. 뒤에 `":00"`을 붙여 `"09:10:00"`으로 만든 뒤 **문자열끼리** 크기를 비교합니다.

**질문: 문자열을 비교하는데 왜 시간 비교가 될까요?**

자릿수가 항상 같은 시간 문자열이기 때문입니다. `"09:14:51"`과 `"09:10:00"`을 앞에서부터 한 글자씩 비교하면 `0`=`0`, `9`=`9`, `:`=`:`, `1`=`1`, 그다음 `4` > `0`에서 승부가 납니다. 사전에서 단어를 찾는 순서(사전순)가 곧 시간 순서와 일치하는 것입니다.

이것이 성립하려면 **자릿수가 반드시 같아야** 합니다. `"9:14"`처럼 앞의 0을 생략하면 `"10:00"`보다 크다고 판정되어 버립니다(`9` > `1`이므로). 6.3절의 제로 패딩이 왜 중요한지 다시 확인되는 대목입니다.

> **💡 심화 질문**
> 이 방식은 자정을 넘는 시간대(예: 23:00 시작, 01:00 지각 기준)에서는 동작하지 않습니다. 왜 그럴까요? 어떻게 고칠 수 있을까요? 학교 수업에서는 문제가 되지 않지만, 야간 근무 관리 시스템이라면 반드시 고려해야 합니다.

## 12.5 findStudent()와 getSheet() — 조연들의 일

```javascript
function findStudent(uid) {
  var rows = getSheet('학생명단', 머리글).getDataRange().getValues();

  // 1행(머리글)은 건너뛰고 한 줄씩 비교
  for (var i = 1; i < rows.length; i++) {
    if (String(rows[i][0]).toUpperCase() === uid) {
      return { name: String(rows[i][1]),
               grade: rows[i][2], klass: rows[i][3], number: rows[i][4] };
    }
  }
  return null;  // 못 찾음 = 미등록
}
```

`getValues()`는 시트 전체를 **2차원 배열**로 가져옵니다. `rows[2][0]`은 3번째 줄의 A열(UID), `rows[2][1]`은 3번째 줄의 B열(이름)입니다.

`i = 1`부터 시작하는 이유는 0번째 줄이 머리글이기 때문입니다.

반복문으로 표를 처음부터 훑어 원하는 값을 찾는 것 — 프로그래밍에서 가장 기본적인 검색 방식입니다. 코딩 입문자에게 가르치기 좋은 예제이기도 합니다.

> **💡 심화 질문**
> "학생이 500명이면 500줄을 다 훑어야 하나요? 느리지 않을까요?"
> 좋은 질문입니다. 실제로 느려집니다. 데이터베이스는 이 문제를 **색인(index)** 으로 해결합니다. 책 뒤의 찾아보기처럼 "어느 값이 몇 번째 줄에 있는지"를 미리 정리해 두는 것입니다. 우리 규모(한 반 30명)에서는 훑어도 순식간이라 단순함을 택했습니다. **"규모에 맞는 방법을 고르는 것"** 도 설계 능력입니다.

```javascript
function getSheet(name, headers) {
  var ss = SpreadsheetApp.getActiveSpreadsheet();
  var sheet = ss.getSheetByName(name);
  if (!sheet) {              // 없으면 만든다
    sheet = ss.insertSheet(name);
    sheet.appendRow(headers);
    sheet.setFrozenRows(1);
  }
  return sheet;
}
```

이 함수가 8.1절에서 말한 **"시트 자동 생성"의 정체**입니다. 시트를 달라고 했을 때 없으면 만들어서 주는 것입니다.

이런 방식을 **"필요할 때 만들기"** 라고 하며, 사용자가 준비 작업을 하지 않아도 되게 만드는 좋은 습관입니다. 우리가 빈 시트에서 바로 시작할 수 있었던 이유가 이 열 줄에 있습니다.

그런데 "필요할 때"만 만들면 작은 불편이 하나 생깁니다. `action=periods`만 호출하면 **교시설정 탭 하나만** 생기는 것입니다. 학생명단은 등록할 때, 출석기록은 출석할 때에야 만들어지니까요. 코드는 정상이지만, 처음 배포한 사람은 "왜 하나만 생기지?" 하고 당황합니다.

그래서 `route()` 맨 앞에 이 한 줄을 두었습니다.

```javascript
function route(e) {
  var p = (e && e.parameter) || {};
  ensureSheets();   // 세 시트가 없으면 한 번에 만들어 둔다
  switch (p.action) { ... }
}

function ensureSheets() {
  getSheet(SHEET_STUDENTS, ['UID','이름','학년','반','번호','등록일시']);
  getSheet(SHEET_LOG, ['날짜','시각','교시','UID','이름','상태','리더기']);
  getPeriodsSheet();
}
```

어떤 요청이든 처음 들어오는 순간 세 시트를 모두 갖춰 둡니다. 이미 있으면 `getSheet()`가 그냥 넘어가므로 반복 호출해도 문제가 없습니다.

**기능이 아니라 사용자의 경험을 위한 코드**입니다. 동작에는 아무 문제가 없었지만, "처음 쓰는 사람이 시트 구조를 한눈에 볼 수 있게" 하려고 넣은 것이죠. 이런 배려가 쌓이면 쓸 만한 도구가 됩니다.

### 10~12장 정리

- `route()`가 `action` 값으로 요청을 여덟 갈래로 나눕니다.
- `startSession()`은 입력을 검증하고 세션 메모를 캐시에 넣습니다.
- `devicePoll()`은 한 단어로, `sessionStatus()`는 JSON으로 같은 세션을 보여 줍니다.
- `deviceTag()`는 잠금으로 보호된 채 등록 또는 출석 처리를 부릅니다.
- `doAttend()`는 미등록·불일치·중복 세 검사를 통과한 뒤에야 기록하고, 시각 문자열 비교로 지각을 판정합니다.
- `findStudent()`는 표를 훑는 검색, `getSheet()`는 없으면 만드는 준비 함수입니다.
