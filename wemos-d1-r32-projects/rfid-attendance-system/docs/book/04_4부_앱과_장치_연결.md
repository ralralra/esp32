# 13장 완성 펌웨어 ① — 설정과 초기화

이제 6장의 `uid_test`에 와이파이와 서버 통신을 더해 완성 펌웨어를 만듭니다.

> 전체 코드: `github.com/ralralra/esp32/blob/main/wemos-d1-r32-projects/rfid-attendance-system/firmware/rfid_attendance/rfid_attendance.ino`

## 13.1 바꿀 곳은 네 줄뿐

```cpp
// ── [설정] 여기 4줄만 바꾸면 됩니다 ─────────────────────
const char* WIFI_SSID  = "와이파이이름";
const char* WIFI_PASS  = "와이파이비밀번호";
const char* RELAY_URL  = "https://script.google.com/macros/s/여기에배포ID/exec";
const char* DEVICE_ID  = "DEV001";   // 앱에 표시되는 리더기 이름
// ──────────────────────────────────────────────────
```

**`WIFI_SSID` / `WIFI_PASS`** — 접속할 와이파이 이름과 비밀번호입니다. **2.4GHz여야 합니다**(4.3절).

**`RELAY_URL`** — 9장에서 배포한 웹 앱 주소입니다. **`/exec`으로 끝나야 합니다.** 개발용 주소인 `/dev`로 끝나면 로그인이 필요해 ESP32가 접속하지 못합니다.

**`DEVICE_ID`** — 이 리더기의 이름입니다. 앱에서 세션을 만들 때 쓰는 이름과 **정확히 같아야** 합니다. 세션은 이 이름을 열쇠로 저장되기 때문에(11.4절), 이름이 다르면 앱이 만든 세션을 이 장치가 영영 못 봅니다. 교실이 여러 개면 `DEV002`, `DEV003`으로 늘리면 됩니다.

설정을 파일 맨 위에 모아 두고 주석으로 감싸 두는 것도 하나의 설계입니다. **"사용자가 고쳐야 할 곳"과 "고치면 안 되는 곳"을 눈에 보이게 나누는 것**이니까요.

## 13.2 setup() — 와이파이에 접속하기까지

```cpp
void setup() {
  Serial.begin(115200);
  pinMode(PIN_LED, OUTPUT);
  pinMode(PIN_BUZZER, OUTPUT);
  digitalWrite(PIN_LED, LOW);

  SPI.begin();
  rfid.PCD_Init();
  delay(100);
  rfid.PCD_SetAntennaGain(MFRC522::RxGain_max);
  rfid.PCD_WriteRegister(MFRC522::GsNReg, 0xF8);
  rfid.PCD_WriteRegister(MFRC522::CWGsPReg, 0x3F);

  Serial.print("와이파이 접속 중");
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.println();
  Serial.print("접속 완료! IP: ");
  Serial.println(WiFi.localIP());
  beep(80); beep(80);   // 준비 완료 알림
}
```

RC522 초기화 부분은 6장과 똑같습니다. **2차시에 검증한 설정을 그대로 가져오는 것**이 중요합니다 — 이미 동작이 확인된 코드를 재사용하면 문제가 생겼을 때 원인의 범위가 좁아집니다.

**`WiFi.mode(WIFI_STA)`** 는 "나는 접속하는 쪽(스테이션)"이라는 선언입니다. ESP32는 반대로 자기가 와이파이를 만드는 공유기 역할(AP 모드)도 할 수 있어서, 어느 쪽인지 정해 줍니다.

**접속을 기다리는 while 문**을 봅시다.

```cpp
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
```

접속될 때까지 0.5초마다 점을 찍으며 기다립니다. 시리얼 모니터에 점이 계속 늘어나기만 한다면 접속에 실패하고 있는 것입니다. 대개 원인은 셋입니다 — 비밀번호 오타, 5GHz 전용 SSID, 신호가 약함.

**`WiFi.localIP()`** 는 공유기가 이 장치에 준 주소를 출력합니다. 이 줄이 나오면 네트워크 연결은 성공입니다. `192.168.0.34` 같은 주소가 보일 텐데, 3.1절에서 말한 "공유기 안에서만 통하는 주소"가 바로 이것입니다.

마지막의 **`beep(80); beep(80);`** 은 사람에게 보내는 신호입니다. 시리얼 모니터를 볼 수 없는 교실 환경에서 "준비됐다"를 알리는 유일한 수단입니다. 소리나 불빛으로 상태를 알리는 것은 임베디드 장치를 만들 때 늘 신경 써야 할 부분입니다.

## 13.3 업로드할 때 나는 그 에러

코드를 붙여넣고 컴파일하면 이런 오류를 만날 수 있습니다.

```
error: redefinition of 'void setup()'
note: 'void setup()' previously defined here
error: redefinition of 'void loop()'
```

**원인은 코드가 아니라 붙여넣기 방법입니다.** Arduino IDE에서 새 스케치를 만들면 이런 빈 틀이 이미 들어 있습니다.

```cpp
void setup() {
  // put your setup code here, to run once:
}

void loop() {
  // put your main code here, to run repeatedly:
}
```

이 위에 우리 코드를 그냥 붙여넣으면 `setup()`과 `loop()`가 두 번씩 정의됩니다. C++에서는 같은 이름의 함수를 두 번 만들 수 없으므로 오류가 납니다.

**해결: 붙여넣기 전에 `Ctrl+A`로 전체 선택하고 `Delete`로 완전히 비우세요.** 앞으로 어떤 코드를 넣을 때도 **"전체 선택 → 삭제 → 붙여넣기"** 순서를 습관으로 만들면 이 오류는 다시 만나지 않습니다.

# 14장 완성 펌웨어 ② — loop의 우선순위 설계

이 장은 **실제로 겪은 실패**에서 출발합니다. 임베디드 프로그래밍에서 가장 중요한 교훈 하나가 여기 들어 있습니다.

## 14.1 처음 만든 loop가 실패한 이유

처음 작성한 `loop()`는 이런 순서였습니다.

```cpp
void loop() {
  // ① 2초마다 서버에 폴링
  if (millis() - lastPoll >= 2000) { ... httpGet(...) ... }

  // ② LED 깜빡이기
  // ③ 카드 확인
}
```

논리적으로는 아무 문제가 없어 보입니다. 그런데 앱과 연동해 테스트하자 두 가지 증상이 나타났습니다.

- **LED가 깜빡이지 않고 켜진 채로 멈춰 있다**
- **시리얼 테스트에서는 잘 읽히던 학생증이, 앱으로 출석체크할 때는 자꾸 인식되지 않는다**

**질문: 왜 그럴까요?**

범인은 ①번의 `httpGet()`이었습니다. HTTPS 요청 한 번에는 암호화 연결을 맺고 데이터를 주고받는 과정이 필요해 **2~3초가 걸립니다.** 그리고 이 함수는 그동안 **아무것도 반환하지 않고 멈춰 있습니다**(블로킹).

`loop()`가 2~3초 동안 ①번에 붙잡혀 있으면 ②번도 ③번도 실행되지 않습니다. 그래서

- LED는 마지막 상태(켜짐)로 얼어붙고
- 카드 스캔은 2초마다 잠깐씩만 이루어져, 그 짧은 틈에 카드를 대지 않으면 놓칩니다

시리얼 테스트(세션 없음)에서는 잘 됐던 이유도 분명해집니다. 그때는 서버 통신이 드물어 스캔할 시간이 충분했던 것입니다.

## 14.2 카드 확인을 맨 앞으로

해결책은 **순서를 바꾸고 간격을 조정하는 것**이었습니다.

```cpp
void loop() {
  // 와이파이가 끊기면 재접속
  if (WiFi.status() != WL_CONNECTED) { WiFi.reconnect(); delay(2000); return; }

  // ① 카드 확인이 최우선
  if (handleCard()) return;

  // ② 세션 중이면 LED 깜빡이기
  if (mode != "IDLE") {
    unsigned long interval = (mode == "REGISTER") ? 150 : 500;
    if (millis() - lastBlink >= interval) {
      lastBlink = millis();
      ledOn = !ledOn;
      digitalWrite(PIN_LED, ledOn ? HIGH : LOW);
    }
  }

  // ③ 서버 폴링 (대기 중 2초 / 세션 중 5초)
  unsigned long pollInterval = (mode == "IDLE") ? POLL_MS : POLL_SESSION_MS;
  if (millis() - lastPoll >= pollInterval) {
    if (handleCard()) return;   // 멈추기 직전에 한 번 더!
    lastPoll = millis();
    String res = httpGet(String(RELAY_URL) + "?action=poll&device=" + DEVICE_ID);
    if (res == "ATTEND" || res == "REGISTER" || res == "IDLE") {
      if (res != mode) Serial.println("모드 변경: " + mode + " → " + res);
      mode = res;
    }
  }
}
```

바뀐 점이 셋입니다.

**첫째, 카드 확인을 맨 앞으로 옮겼습니다.** `loop()`는 1초에 수백 번 돕니다. 폴링에 붙잡히지 않은 시간 전부가 카드 스캔에 쓰입니다.

**둘째, 폴링 직전에 카드를 한 번 더 확인합니다.**

```cpp
    if (handleCard()) return;   // 멈추기 직전에 한 번 더!
```

이 한 줄이 영리한 부분입니다. 이제 2~3초 동안 멈출 참인데, 만약 학생이 지금 막 카드를 올려놓았다면? 그대로 폴링에 들어가면 그 카드는 최대 3초를 기다려야 합니다. 그래서 **"멈추기 직전에 한 번 더 확인"** 하는 것입니다.

**셋째, 세션 중에는 폴링 간격을 5초로 늘렸습니다.**

```cpp
const unsigned long POLL_MS = 2000;          // 대기 중
const unsigned long POLL_SESSION_MS = 5000;  // 세션 중
```

**질문: 세션 중이면 더 자주 물어봐야 하는 것 아닌가요?**

반대입니다. 세션 중에 ESP32가 해야 할 일은 **카드를 스캔하는 것**이지 서버에 묻는 것이 아닙니다. 세션이 시작됐다는 사실은 이미 알고 있으니까요. 그러니 이때는 폴링을 줄이고 스캔에 시간을 몰아주는 것이 맞습니다.

대기 중에는 반대로 2초를 유지합니다. 앱에서 버튼을 눌렀을 때 빨리 반응해야 하기 때문입니다.

> **📌 이 장의 핵심 교훈**
> **느린 작업이 빠른 작업을 막지 않게 하라.**
> 임베디드 프로그래밍에서 반복해서 마주치는 원칙입니다. 통신·파일 저장처럼 오래 걸리는 일과, 버튼·센서처럼 즉시 반응해야 하는 일이 한 흐름에 섞여 있으면 반드시 이런 문제가 생깁니다. 규모가 커지면 작업을 여러 갈래로 나누어 동시에 돌리는 방법(멀티태스킹, 인터럽트)을 쓰지만, 우리 규모에서는 **순서와 간격을 조절하는 것**만으로 충분히 해결됩니다.

## 14.3 delay 대신 millis를 쓰는 이유

LED 깜빡임 코드를 다시 봅시다.

```cpp
    if (millis() - lastBlink >= interval) {
      lastBlink = millis();
      ledOn = !ledOn;
      digitalWrite(PIN_LED, ledOn ? HIGH : LOW);
    }
```

LED를 0.5초마다 깜빡이려면 이렇게 쓰고 싶어집니다.

```cpp
  digitalWrite(PIN_LED, HIGH);
  delay(500);
  digitalWrite(PIN_LED, LOW);
  delay(500);
```

간단하지만 **써서는 안 됩니다.** `delay(500)` 동안 ESP32는 아무것도 못 합니다. 카드를 대도 못 읽고 서버 폴링도 못 합니다. 14.1절에서 본 문제와 똑같은 상황을 우리 손으로 만드는 셈입니다.

`millis()`는 보드가 켜진 뒤 흐른 시간을 밀리초로 알려 주는 함수입니다. 이것을 쓰면 **기다리지 않고 시간을 잽니다.**

- `lastBlink`에 마지막으로 LED를 바꾼 시각을 적어 둔다
- 매번 `loop()`를 돌 때마다 "지금이 그때보다 500ms 이상 지났나?"만 확인한다
- 아직이면 아무것도 하지 않고 그냥 지나간다

시계를 힐끔 보고 "아직이네" 하고 하던 일을 계속하는 것과 같습니다. 이 패턴을 익히면 여러 가지 일을 동시에 하는 것처럼 보이는 프로그램을 만들 수 있습니다.

`ledOn = !ledOn`은 참/거짓을 뒤집는 것입니다. 켜져 있으면 끄고, 꺼져 있으면 켭니다.

## 14.4 LED로 상태를 말하기

우리 장치에는 화면이 없습니다. 그래서 LED 하나로 상태를 전달합니다.

| LED 상태 | 뜻 |
|---|---|
| 꺼짐 | 대기 중 (세션 없음) |
| **0.5초 간격 깜빡** | 출석 세션 — 학생증을 태그하세요 |
| **0.15초 간격 빠른 깜빡** | 등록 세션 — 새 학생증을 태그하세요 |
| 계속 켜짐 | 태그를 처리하며 서버와 통신 중 |

깜빡임 속도만으로 출석과 등록을 구분할 수 있다는 점이 실용적입니다. 학생은 장치만 보고도 "지금 태그하면 되는구나"를 압니다.

부저도 같은 역할입니다.

| 소리 | 뜻 |
|---|---|
| 삑삑 (짧게 2번) | 성공 (출석 기록됨 / 등록됨) |
| 삐— (길게 1번) | 실패 (미등록·중복·다른 학생·중복 출석) |

**소리와 빛으로 상태를 알리는 설계**는 화면 없는 장치의 사용성을 결정합니다. 여러분이 만든 장치를 처음 보는 사람이 설명서 없이 쓸 수 있는지 — 이것이 좋은 설계의 기준입니다.

### 14장 정리

- HTTPS 요청은 2~3초간 모든 것을 멈춥니다. 이것이 LED 정지와 인식 실패의 원인이었습니다.
- 카드 확인을 맨 앞에 두고, 폴링 직전에 한 번 더 확인하고, 세션 중 폴링 간격을 늘려 해결했습니다.
- `delay()` 대신 `millis()` 비교를 쓰면 기다리지 않고 시간을 잴 수 있습니다.
- LED 깜빡임 속도와 부저 소리로 화면 없이 상태를 전달합니다.

# 15장 완성 펌웨어 ③ — 카드를 읽고 서버에 보내기

## 15.1 cardTagged() — 잠든 카드를 깨우는 법

6장의 `uid_test`에서는 `PICC_IsNewCardPresent()`로 카드를 찾았습니다. 완성 펌웨어는 다른 방법을 씁니다.

```cpp
bool cardTagged() {
  // WUPA: HALT 상태 카드까지 깨워서 감지
  byte atqa[2];
  byte atqaSize = sizeof(atqa);
  MFRC522::StatusCode st = rfid.PICC_WakeupA(atqa, &atqaSize);
  if (st != MFRC522::STATUS_OK && st != MFRC522::STATUS_COLLISION)
    return false;
  return rfid.PICC_ReadCardSerial();
}
```

**REQA와 WUPA의 차이**를 알아야 합니다. 둘 다 리더기가 "거기 카드 있나요?"라고 묻는 신호인데, 대답하는 조건이 다릅니다.

- **REQA** (`PICC_IsNewCardPresent`) — 깨어 있는 카드만 대답합니다
- **WUPA** (`PICC_WakeupA`) — **잠든(HALT) 카드까지 깨워서** 대답하게 합니다

카드는 한 번 통신을 마치면 `PICC_HaltA()`에 의해 잠듭니다(6.3절). 또 어떤 스마트카드는 처음부터 REQA에 잘 응답하지 않기도 합니다. 실제로 학생증이 인식되지 않던 문제를 해결하는 과정에서, 송신 출력 부스트와 함께 이 WUPA 방식이 결정적이었습니다.

`STATUS_COLLISION`도 성공으로 치는 이유는, 카드가 두 장 이상 겹쳐 있어 신호가 충돌한 경우에도 "카드는 있다"는 뜻이기 때문입니다.

## 15.2 readUid() — 바이트를 사람이 읽는 글자로

```cpp
String readUid() {
  String uid = "";
  for (byte i = 0; i < rfid.uid.size; i++) {
    if (rfid.uid.uidByte[i] < 0x10) uid += "0";
    uid += String(rfid.uid.uidByte[i], HEX);
  }
  uid.toUpperCase();
  return uid;
}
```

6.3절에서 본 코드를 함수로 분리한 것입니다. 두 곳(세션 중, 대기 중)에서 쓰이므로 함수로 빼는 것이 자연스럽습니다.

**같은 코드를 두 번 쓰게 되면 함수로 만든다** — 리팩터링의 가장 기본적인 신호입니다.

여기서 만들어진 문자열이 서버로 전송되고, 그대로 구글 시트에 저장되며, 등록할 때 저장된 값과 비교됩니다. **형식이 처음부터 끝까지 일치해야** 하는 이유입니다. 대문자 통일과 제로 패딩이 그래서 중요합니다.

## 15.3 handleCard() — 세션이 있을 때와 없을 때

```cpp
bool handleCard() {
  if (!cardTagged()) return false;

  String uid = readUid();
  rfid.PICC_HaltA();
  rfid.PCD_StopCrypto1();

  if (mode == "IDLE") {
    // 세션이 없을 때도 카드가 읽히는지 확인할 수 있게 출력만
    Serial.println("카드 인식 (세션 없음 → 전송 안 함): UID = " + uid);
    delay(1000);
    return true;
  }

  Serial.println("태그됨! UID = " + uid + " → 서버 전송");
  digitalWrite(PIN_LED, HIGH);

  String res = httpGet(String(RELAY_URL) + "?action=tag&device="
                       + DEVICE_ID + "&uid=" + uid);
  handleTagResult(res);

  mode = "IDLE";
  digitalWrite(PIN_LED, LOW);
  lastPoll = millis();
  delay(1000);
  return true;
}
```

**반환값이 `bool`인 이유**부터 봅시다. `loop()`에서 `if (handleCard()) return;`처럼 쓰기 위해서입니다. 카드를 처리했으면 `true`를 돌려주어 `loop()`가 이번 회차를 즉시 끝내게 합니다. 카드가 없으면 `false`를 주어 LED와 폴링으로 넘어가게 합니다.

**세션이 없을 때(IDLE)의 처리**가 이 함수의 좋은 점입니다. 서버로 보내지 않고 시리얼에만 출력합니다. 덕분에 **앱이나 서버 없이도 현장에서 카드 인식을 시험할 수 있습니다.** 리더기 위치를 조정하거나 새 카드의 인식 여부를 확인할 때 아주 유용합니다.

**세션 중의 처리**는 이렇게 이어집니다. LED를 계속 켜서 "처리 중"을 표시하고, 서버로 UID를 보내고, 응답에 따라 부저를 울리고(`handleTagResult`), 모드를 `IDLE`로 되돌립니다.

`lastPoll = millis();`는 방금 서버와 통신했으니 폴링 시계를 지금으로 맞추는 것입니다. 통신이 연달아 일어나는 것을 막습니다.

`delay(1000)`은 같은 카드가 연속으로 처리되는 것을 막습니다.

**응답에 따른 반응**은 이렇게 나뉩니다.

```cpp
void handleTagResult(String res) {
  if (res.startsWith("OK_REG"))       { /* 등록 성공 */ beep(80); beep(80); }
  else if (res.startsWith("OK"))      { /* 출석 성공 */ beep(80); beep(80); }
  else if (res.startsWith("UNKNOWN")) { /* 미등록 */    beep(600); }
  else if (res.startsWith("DUP"))     { /* 중복 카드 */ beep(600); }
  else if (res.startsWith("MISMATCH")){ /* 다른 학생 */ beep(600); }
  else if (res.startsWith("ALREADY")) { /* 중복 출석 */ beep(600); }
  else                                { /* 그 밖 */     beep(600); }
}
```

서버가 보낸 한 줄의 **첫 단어만 보고** 판단합니다. `startsWith()`는 문자열이 특정 글자로 시작하는지 확인하는 함수입니다.

**`OK_REG`를 `OK`보다 먼저 검사하는 순서에 주의하세요.** `"OK_REG,김세이프"`는 `"OK"`로도 시작하므로, 순서를 바꾸면 등록 결과가 출석 처리로 잘못 분류됩니다. 조건문의 순서가 의미를 갖는 사례입니다.

## 15.4 httpGet() — 리다이렉트라는 함정

```cpp
String httpGet(String url) {
  WiFiClientSecure client;
  client.setInsecure();   // 인증서 검증 생략

  HTTPClient https;
  // Apps Script 리다이렉트 따라가기 (필수!)
  https.setFollowRedirects(HTTPC_STRICT_FOLLOW_REDIRECTS);
  https.setTimeout(10000);

  String body = "";
  if (https.begin(client, url)) {
    int code = https.GET();
    if (code == HTTP_CODE_OK) {
      body = https.getString();
      body.trim();
    }
    https.end();
  }
  return body;
}
```

이 함수는 짧지만 **연동 실패의 1순위 원인**이 숨어 있습니다.

### 함정 ① 리다이렉트를 따라가야 한다

```cpp
  https.setFollowRedirects(HTTPC_STRICT_FOLLOW_REDIRECTS);
```

Apps Script 웹 앱에 요청하면, 서버는 답을 바로 주지 않고 **"이 주소로 다시 가세요"라고 다른 주소를 알려 줍니다**(HTTP 302 리다이렉트). 브라우저는 이것을 자동으로 따라가기 때문에 우리가 눈치채지 못합니다.

하지만 ESP32의 HTTPClient는 **기본적으로 따라가지 않습니다.** 그래서 이 줄이 없으면 응답이 항상 빈 문자열이 되고, 아무리 서버가 정상이어도 연동이 되지 않습니다. 원인을 찾기 어려운 종류의 문제라, 이 한 줄을 꼭 기억해 두세요.

### 함정 ② 인증서 검증

```cpp
  client.setInsecure();
```

HTTPS 통신에서는 상대가 진짜 그 서버인지 인증서로 확인하는 절차가 있습니다. 제대로 하려면 구글의 루트 인증서를 코드에 넣고 관리해야 하는데, 인증서는 주기적으로 갱신되므로 교육용으로는 부담이 큽니다.

`setInsecure()`는 이 검증을 생략합니다. **통신 자체는 여전히 HTTPS로 암호화되지만**, "상대가 진짜 구글인지"는 확인하지 않는 상태가 됩니다.

교실 환경에서는 실용적인 선택이지만, 이것이 어떤 위험을 남기는지는 알아 둘 가치가 있습니다. 중간에서 통신을 가로채는 공격(중간자 공격)을 이론적으로 막지 못하기 때문입니다. **편의와 보안 사이의 맞바꿈**이 어떻게 이루어지는지 보여 주는 좋은 사례입니다.

### 함정 ③ 타임아웃

```cpp
  https.setTimeout(10000);
```

서버가 응답하지 않을 때 영원히 기다리지 않도록 10초 제한을 둡니다. 이것이 없으면 서버 장애 한 번에 장치가 멈춰 버릴 수 있습니다.

### ESP32가 하는 일은 브라우저와 같다

이 함수의 정체는 결국 **"주소를 열고 돌아온 글자를 받아오는 것"** 입니다. 브라우저가 하는 일과 똑같습니다.

이 사실을 알면 디버깅이 쉬워집니다. ESP32에서 문제가 생기면, **같은 주소를 브라우저에서 열어 보면 됩니다.**

- 브라우저에서 정상 응답 + ESP32에서 실패 → 장치나 네트워크 문제
- 브라우저에서도 실패 → 서버 문제

문제의 범위를 절반으로 줄이는 이 방법을, 학생들에게 꼭 알려 주세요.

---

### 15장 정리

- `cardTagged()`는 WUPA로 잠든 카드까지 깨워 감지합니다.
- `readUid()`는 UID를 항상 같은 형식(대문자 16진수)의 문자열로 만듭니다.
- `handleCard()`는 세션이 없으면 출력만, 있으면 서버로 전송합니다.
- `httpGet()`에서 리다이렉트 따라가기 설정을 빠뜨리면 응답이 늘 비어 옵니다.
- ESP32의 통신은 브라우저로 같은 주소를 여는 것과 같아, 문제 범위를 나누어 진단할 수 있습니다.

# 16장 앱 만들기와 연동

## 16.1 프롬프트 하나로 앱 만들기

앱은 AI Studio에서 만듭니다. 저장소에 준비된 프롬프트를 쓰면 됩니다.

> `github.com/ralralra/esp32/blob/main/wemos-d1-r32-projects/rfid-attendance-system/docs/app_build_prompt.md`

1. 프롬프트 문서를 엽니다
2. `{{중계서버URL}}` 부분을 9장에서 배포한 실제 주소로 바꿉니다
3. 프롬프트 전체를 AI Studio에 붙여넣습니다
4. 만들어진 앱을 배포합니다

프롬프트에는 화면 구성(3개 탭)뿐 아니라 **통신 규칙과 주의사항까지** 적혀 있습니다. AI에게 "예쁜 출석 앱 만들어 줘"라고만 하면 우리 서버와 대화하지 못하는 앱이 나오지만, 규격을 정확히 알려 주면 바로 동작하는 앱이 나옵니다.

**"AI에게 정확한 명세를 주면 정확한 결과가 나온다"** — 이 자체가 좋은 수업 소재입니다. 프롬프트 문서를 학생들과 함께 읽으며 "이 문장이 없으면 어떤 문제가 생길까?"를 토론해 보세요.

만들어지는 앱의 화면은 셋입니다.

| 탭 | 하는 일 |
|---|---|
| **출석체크** | 교시·학생 선택 → 시작 → 30초 대기 → 결과(출석/지각 배지) |
| **학생 관리** | 학생 정보 입력 → 등록 시작 → 태그 → 학생증 등록. 등록 목록 조회 |
| **출결 기록** | 날짜·교시 필터로 기록 조회 + 출석/지각 요약 |

## 16.2 앱이 하는 일은 두 가지뿐

앱 코드가 복잡해 보여도, 서버와의 대화는 **시작하고, 묻는 것** 두 가지가 전부입니다.

```javascript
// 요청 도우미: GET + URL 파라미터만
async function relay(params) {
  const qs = new URLSearchParams(params).toString();
  const res = await fetch(`${RELAY_URL}?${qs}`);
  return JSON.parse(await res.text());
}
```

`URLSearchParams`는 `{action:'start', device:'DEV001'}` 같은 객체를 `action=start&device=DEV001` 문자열로 바꿔 줍니다. 한글이나 특수문자가 있어도 알아서 안전하게 변환해 줍니다.

**① 시작하기**

```javascript
relay({ action: 'start', mode: 'attend',
  device: 'DEV001', period: '1',
  name: '김세이프', timeout: '30' });
```

이 한 번의 호출로 서버에 세션 메모가 생기고, 2초 안에 ESP32가 그것을 발견합니다.

**② 묻기**

```javascript
const s = await relay({ action: 'status', device: 'DEV001' });
if (s.state === 'done') {
  showResult(s.result);
  // { ok: true, name: '김세이프', status: '지각', time: '21:22:58' }
} else if (s.state === 'none') {
  showTimeout();  // 30초 초과
}
```

1초마다 이것을 반복하다가 `done`이면 결과를, `none`이면 시간 초과를 보여 줍니다.

**ESP32의 폴링 코드와 나란히 놓고 보세요.**

```cpp
// ESP32 (C++)
String res = httpGet(RELAY_URL + "?action=poll&device=" + DEVICE_ID);
if (res == "ATTEND") { ... }
```

```javascript
// 앱 (JavaScript)
const s = await relay({ action: 'status', device: 'DEV001' });
if (s.state === 'done') { ... }
```

**언어는 다르지만 구조는 똑같습니다.** 주소를 만들고, 요청하고, 답에 따라 분기합니다. 이것이 이 책 전체의 종합 정리에 해당하는 관찰입니다 — 서로 다른 두 세계가 같은 약속(프로토콜) 위에서 만난다는 것.

## 16.3 CORS — 브라우저의 검문소

앱 코드에서 지켜야 할 규칙이 하나 있습니다.

> **fetch에 커스텀 헤더를 붙이지 마세요.**

`Content-Type: application/json` 같은 헤더를 붙이면 요청이 실패합니다. 이유는 **CORS**(교차 출처 리소스 공유)라는 브라우저의 보안 장치 때문입니다.

브라우저는 웹페이지가 **다른 서버**로 요청을 보낼 때 검문을 합니다. 악성 사이트가 여러분 몰래 다른 사이트에 요청을 보내는 것을 막기 위해서입니다.

그런데 이 검문에는 등급이 있습니다.

- **단순 요청**(GET에 특별한 헤더 없음) → 검문 없이 바로 통과
- **복잡한 요청**(커스텀 헤더, PUT/DELETE 등) → 먼저 "이런 요청 보내도 되나요?"라고 사전 확인(preflight)을 보냄

Apps Script는 이 사전 확인에 제대로 답하지 않습니다. 그래서 복잡한 요청은 실패합니다.

**해법은 단순 요청만 쓰는 것** — 우리가 처음부터 GET과 URL 파라미터만 쓴 이유가 여기 있습니다(10.2절). 제약을 피해 설계를 단순하게 만든 사례입니다.

## 16.4 시뮬레이션 버튼의 쓸모

앱의 대기 화면 아래에는 **[테스트] ESP32 RFID 태그 시뮬레이션** 버튼이 있습니다. 이 버튼은 앱 내부에서 가짜 결과를 만드는 것이 **아니라**, 진짜 서버에 태그 요청을 보냅니다.

```javascript
relay({ action: 'tag', device: 'DEV001', uid: 'TEST0001' });
```

ESP32가 하는 일과 **완전히 같은 경로**입니다. 그래서 이 버튼 하나로 얻는 것이 많습니다.

- **하드웨어 없이 앱 전체를 시험**할 수 있습니다
- **문제의 범위를 나눌 수 있습니다** — 시뮬레이션은 되는데 실제 태그가 안 되면 장치 문제, 시뮬레이션도 안 되면 앱이나 서버 문제
- **수업 시연이 쉬워집니다** — 부품이 부족한 학급에서도 흐름을 보여 줄 수 있습니다

**테스트용 장치를 실제와 같은 경로로 만들어 두는 것** — 규모가 큰 개발에서도 쓰는 방법입니다. 가짜로 만들어 두면 정작 실물이 왔을 때 다른 문제가 튀어나오기 때문입니다.

### 16장 정리

- 앱은 프롬프트에 서버 주소만 넣으면 만들어집니다.
- 앱이 하는 일은 세션 시작과 결과 폴링 두 가지뿐입니다.
- CORS 때문에 GET + URL 파라미터만 쓰고, 커스텀 헤더는 붙이지 않습니다.
- 시뮬레이션 버튼은 실제와 같은 경로로 동작해, 하드웨어 없는 시험과 문제 범위 좁히기에 쓰입니다.

### 실습 과제

1. 앱에서 학생증을 등록하고, 구글 시트의 학생명단에 6장에서 기록해 둔 UID가 그대로 들어갔는지 확인하세요.
2. 등록되지 않은 카드로 출석을 시도해 보세요. 앱 화면과 부저 소리가 어떻게 다른가요?
3. 시뮬레이션 버튼과 실제 태그를 각각 해 보고, 서버 입장에서 무엇이 다른지 설명해 보세요.
